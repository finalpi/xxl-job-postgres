# 3.4.0 执行器兼容说明

本 fork 的调度中心仍基于 `3.5.1-SNAPSHOT`，增加了对原版 `xxl-job-core:3.4.0` 和 `2.4.0` 执行器的双向协议适配。目标是让已接入的业务后端继续使用原来的 SDK 和任务 Handler。

## 兼容范围

| 行为 | 3.4.0 协议 | 处理方式 |
| --- | --- | --- |
| 注册和注销 | 没有 `XXL-JOB-APPNAME` 请求头 | 从 `registryKey` 识别已存在的执行器组，并校验该组令牌 |
| 调度任务 | `/run` | 只向已注册为旧协议的地址调用 `/run`，不先调用 `/trigger` 再重试 |
| 执行回调 | JSON 数组，时间字段为 `logDateTim` | 转换为当前内部回调类型，整批鉴权后才进入处理队列 |
| 执行日志 | 请求字段为 `logDateTim` | 将当前请求的 `logDateTime` 转换为旧字段 |
| 心跳、空闲检查、终止任务 | `/beat`、`/idleBeat`、`/kill` | 使用旧协议客户端调用，保持原路径和返回结构 |
| 新版任务管理 API | 旧 SDK 没有这些入口 | 缺少应用名请求头时不允许调用新增、修改、启停和触发等管理接口 |

带应用名请求头的注册请求必须与 Body 的执行器组一致。空请求头、错误组名或错误令牌不会自动降级为旧协议。旧回调按日志所属组核验令牌；一批回调只要包含无权限组的日志，整批拒绝，不会先处理其中一部分。已过期日志保持上游忽略行为，但请求仍需有效组令牌。

2.4.0 的日志响应使用 `content`、3.4.0 使用 `data`，适配器同时解析两种封装。两个版本均通过真实 SDK 测试。

不承诺兼容其他 2.x、3.0—3.3、修改过的私有协议，或旧 SDK 中上游尚未修复的问题。本次不修改原版 3.4.0 SDK。

## 新旧执行器同时接入

协议记录在 `xxl_job_registry.executor_protocol`，取值为 `CURRENT` 或 `V3_4_0`。它与现有的注册组、应用名和地址共用唯一键，因此同一执行器组内也可以同时运行新旧节点。

心跳会更新协议字段；多个调度中心共用数据库记录。HTTP 客户端缓存的容量阈值为 1000，存活时间为 5 秒，最多在这段时间后重新读取其他实例识别的协议。相同地址升级 SDK 后，需要先完成心跳，并等待缓存过期再接收任务。没有注册记录的地址按当前协议处理；旧执行器必须先成功注册，不能依赖手工地址配置来推断版本。

现有注册记录的超时和注销机制保持不变。旧协议使用自己的客户端，不通过任务失败后的自动重发探测版本，避免一次触发在新旧路径上执行两次。

## 配置

| 配置键 | 默认值 | 用途 |
| --- | --- | --- |
| `xxl.job.compatibility.v340.enabled` | `true` | 是否接受旧注册、旧回调，以及调用旧执行器；可通过 `XXL_JOB_COMPATIBILITY_V340_ENABLED=false` 关闭 |
| `xxl.job.accessToken` | 空 | 保留 3.4.0 的旧全局令牌配置，只供未填写组令牌的执行器组使用 |
| `XXL_JOB_LEGACY_ACCESS_TOKEN` | 空 | 容器环境中设置上述旧全局令牌的入口 |

优先使用数据库中每个执行器组自己的 `access_token`。如果组已有非空令牌，旧全局令牌不能覆盖它；只有组令牌为空时才使用全局令牌。没有可用令牌的旧执行器拒绝注册和调度，不支持无令牌降级。当前协议仍要求应用名请求头和该组令牌，不使用旧全局令牌兜底。

迁移旧数据库时，可以将各组令牌设置成对应旧执行器当前使用的令牌；也可以保留旧组令牌为空，并通过 Secret 设置旧全局令牌。不要将真实令牌写进镜像、SQL 文件或版本库。

## 已安装 PostgreSQL fork 的升级

更新镜像之前，在维护窗口执行：

```sh
psql -d xxl_job -v ON_ERROR_STOP=1 -f doc/db/migrations/20261029_legacy_executor_protocol.sql
```

脚本可重复执行，只新增带缺省值的协议字段；新安装执行当前建表脚本时已包含该列。旧记录的缺省协议为 `CURRENT`，旧 SDK 第一次成功注册后自动改成 `V3_4_0`。不根据地址、SN、组名或历史部署推测协议。

## 从 222 的 3.4.0 调度中心切换

此兼容层不包含生产环境部署或 MySQL 到 PostgreSQL 的数据迁移。要让业务后端不改代码，还需保留以下接入条件：

1. 原调度服务的地址、端口和上下文路径。例如原地址使用 `/xxl-job-admin` 时，新容器需设置 `SERVER_SERVLET_CONTEXT_PATH=/xxl-job-admin`，并保留对应 Service/代理入口。
2. 原执行器应用名、令牌、任务 ID、Handler 名称、调度参数和运行状态。任务及权限数据迁移后需逐项核对，兼容协议不会自动搬迁数据库内容。
3. 旧执行器能访问新调度中心，新调度中心也能回连原执行器地址。

222 当前的 `xxl.job.logretentiondays=1` 在此 fork 中表示禁用到期清理，升级时需改成至少 3 天；现有基于 MySQL 的日志清理 CronJob 也需要替换或停用，改由 PostgreSQL 分区维护完成明细回收。

切换时先停止旧调度中心的任务分发，再启用新中心，避免双重调度。回滚需同时恢复原数据库、镜像和接入配置；已经回收的日志分区需从备份恢复。

## 测试

`compatibility-tests/legacy-executor` 使用独立 POM，分别固定依赖 Maven Central 的 `xxl-job-core:3.4.0` 和 `2.4.0` 及其原有传递依赖（2.4.0 工程位于 `compatibility-tests/legacy24-executor`）。测试通过独立 JVM 启动它，并检查实际加载的 Jar 路径，防止误用当前 SDK 得出兼容结论。该依赖只参与测试，不打入调度中心运行镜像。

```sh
mvn -B -ntp -pl xxl-job-admin -am -Dmaven.javadoc.skip=true -Dgpg.skip=true verify
```

除了原有 PostgreSQL、日志分区和当前执行器测试，新增测试覆盖：真实 3.4.0 和 2.4.0 执行器注册与注销、Cron 和手工调度、成功/失败回调、日志内容读取、忙闲检查、终止任务、同组新旧执行器混用、协议缓存更新、禁用兼容、错误令牌、跨组和混合批次回调、500 条以上回调批次及旧全局令牌的适用范围。

GitHub Actions 在 PostgreSQL 14/16/18 与 amd64/arm64 的 6 种组合中执行同一套测试，再构建和发布镜像。
